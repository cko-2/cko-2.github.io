## The benefits of effort estimation tracking

Within my final project, I did not put much work into effort estimation. While each estimation took no longer than a minuite, that is not to say that these were done thoughtlessly or that I held little value for such things. I knew what I was capable of, had time to go out of the bounds by a good amount, and would have rather spent the time on working on the actual project implementation itself. Within effort estimation, you need to take into account how an issue is implemented, which is usually done at the time of issue creation, not estimate creation. For example, I would not be creating an issue such as "Account Management" when there are many parts that can come into play below the surface. Password hashes, admin functions, username mapping, all of these are parts that should each have its own issue. When we combine issues broadly, we become unable to estimate accurately. Back to my personal effort estimations, I spent little time on creating estimations because my issues were broken down into smaller, less complex pieces, that had clear goals for implementation. Providing a separate estimate on each small part proves to be more accurate at estimation, like how in my final project, we had an issue for M1: Home Page Mockup. This can be easily estimated since we had done similar exercises in class before, and have timed each attempt with creating mockup pages using Bootstrap, Nextjs, and Postgresql.

Being able to track effort accurately in a short amount of time provided major benefits to the project and ensured timely completion. By providing estimates, we were able to evenly distribute the workload, and know how much time needed to be allocated towards each issue before the deadline. The actual estimation was very useful, since I had originally been too unambitious with the project content. I had stated that tag functionality would be a future addition, however, there was little work to be done in milestone 2, which caused us to realize that there were more refinements that could be made before hte project deadline.

## How to track?

We tracked effort by letting each member estimate for their own issue on GitHub Projects. We believe that each person is capable of accurately providing accurate estimates for themselves. If I were to estimate for another member, it may seem like I am expecting too much of them, or giving them too little work. By letting each member estimate for themself, we can distribute workload fairly, not just equally. While our estimates may have not been completely accurate, they weren't skewed in any way overall. Some were overstated, some were understated. We did not have any outliers which is important since this means that our estimates were mostly accurate. Next time, I would like to split the issues down and break it into separate tasks even more so that we can be more accurate with our estimations. Issues that we had in our project such as "Create Password Hash" were comepletely new to any of us, and we did not have a good way to estimate this process. Next time, I would research the process and outline it more so that the estimation can be improved. No AI was used in estimation, however I did take into account that with my usage of Claude Code within the project, I was able to take on larger issues and estimated shorter times for my issues.
